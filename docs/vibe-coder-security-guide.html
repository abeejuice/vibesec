PRE-OP: THINK BEFORE YOU VIBE

Before you open Cursor or type a single prompt — answer these 5 questions. Most security failures happen because nobody asked them at the start.

What data am I collecting, and do I actually need all of it?

GDPR and data minimisation law: you're only allowed to collect what's necessary. Less data = less liability. Are you storing email, location, health info? Why?

Who can access what — do I even need auth?

A public med reference tool needs no auth. A tool that stores user data absolutely does. Decide this before Cursor writes your routes.

What's the worst-case scenario if this gets hacked?

Walk through the nightmare: API bill of ₹50,000, patient data exposed, your name on a breach notice. If that's unacceptable, your security posture must match the risk.

Am I handling any PHI or PII?

If your app touches anything that could identify a patient — symptoms, diagnoses, contact info — you are in regulatory territory. HIPAA (US), DPDP Act (India), GDPR (EU) all apply.

What's my incident response plan?

If your .env leaks tonight, what do you do first? Write the answer before you ship. The plan below in the ICU section is your template.

// LEGAL MINIMUM — DO THIS BEFORE YOU COLLECT DATA

COMPLIANCE BASELINE (from Reddit vibe-coding guide)
  • Publish a privacy policy — even a simple one. Describe what you collect and why.
  • Document how you store and handle user data (encrypted at rest? who has DB access?).
  • Don't do anything obviously dodgy with user info — selling it, sharing it, using it to train models without consent.
  • If you collect any EU user data: GDPR applies. If Indian users: DPDP Act 2023 applies.
  • You don't need to be perfect — but you need to not be reckless.

🔴 CRITICAL — INSTANT GAME-OVER IF MISSED
C-01
CRITICAL

API KEYS HARDCODED IN FRONTEND JS

If your key is in the browser, assume it's already been taken. Anyone who opens DevTools can read it. Cursor does this constantly.

SHOW FIX

❌ BAD — WHAT CURSOR OFTEN GENERATES

frontend/api.js
const response = await fetch('https://api.openai.com/v1/...', {
headers: { 'Authorization': 'Bearer sk-proj-abc123YOURKEYHERE' }
});
// This key is now PUBLIC — anyone in DevTools can read it

✅ FIXED — KEY MOVED TO BACKEND ONLY

backend/routes/ai.js
// Key lives ONLY in .env on the server
const apiKey = process.env.OPENAI_API_KEY;
const response = await fetch('https://api.openai.com/v1/...', {
headers: { 'Authorization': `Bearer ${apiKey}` }
});
// Frontend calls YOUR backend proxy, never OpenAI directly

"Audit my entire codebase for any API keys, secrets, or tokens hardcoded in frontend files. Move all of them to server-side environment variables. Create a backend proxy route for any external API calls the frontend was making directly. Show me every file you change."

C-02
CRITICAL

.ENV COMMITTED TO GIT — EVEN ONCE

It's in the history even if you deleted the file. git log can find it instantly. Every key in that file must be rotated.

SHOW FIX

❌ BAD — .env visible in git history

terminal
git add .
git commit -m "initial"
# .env was not in .gitignore — it's now in history forever
git rm .env
# Too late. It's still in the commit history.

✅ FIXED — proper .gitignore from the start

.gitignore
.env
.env.local
.env.production
.env*.local
# Commit .env.example with dummy values instead

"Check my .gitignore and confirm it properly excludes all .env files and any other sensitive config. Also check if any .env files have ever been committed to this repo's history. If so, tell me exactly which commits and what I need to do to purge them."

C-03
CRITICAL

ADMIN ROUTES PROTECTED ONLY IN THE FRONTEND

The server doesn't care about your React Router guards. Hit the endpoint directly and it opens right up. Every route must be protected server-side.

SHOW FIX

❌ BAD — frontend-only "protection"

App.jsx
{"{"}{isAdmin ? <AdminPanel /> : <Redirect to="/" />{"}"}
// The backend route /api/admin is still wide open
// curl https://yourapp.com/api/admin/users ← works fine

✅ FIXED — server-side auth middleware

backend/routes/admin.js
router.use(requireAuth); // must be logged in
router.use(requireRole('admin')); // must be admin role
router.get('/users', getUsers);
// Frontend guards are UX only — server guards are security

"Audit every API route in my backend. For each route, tell me: what auth middleware is applied, whether it requires a specific role, and whether it could be accessed without authentication. Flag any route that handles sensitive data or admin actions without server-side auth middleware."

C-04
CRITICAL

SQL INJECTION VIA STRING CONCATENATION

Building SQL with user input strings is a decades-old vulnerability AI tools still generate. One crafted input and your entire database is readable or deleted.

SHOW FIX

❌ BAD — string concatenation

queries.js
const query = "SELECT * FROM users WHERE id=" + userId;
// userId = "1 OR 1=1; DROP TABLE users; --"
// Your database is now gone.

✅ FIXED — parameterised queries

queries.js
const query = "SELECT * FROM users WHERE id = $1";
const result = await db.query(query, [userId]);
// userId is passed as a parameter, never interpolated

"Search my entire codebase for any SQL queries that use string concatenation or template literals with user-supplied values. Replace every one with parameterised queries. Show me each change."

C-05
CRITICAL

AUTH MIDDLEWARE MISSING ON INTERNAL API ROUTES

AI adds middleware to obvious routes and skips the rest. Audit every single endpoint. Assume nothing is protected until you verify it.

SHOW FIX

"List every API route in my application. For each one, explicitly state whether it has authentication middleware, what that middleware checks, and whether the protection is sufficient for the data it handles. Flag any that are missing auth or have weak protection."

🟠 HIGH — FIX BEFORE YOU SHARE A LINK
H-06
HIGH

NO RATE LIMITING ON /LOGIN

Bots can try 10,000 password combos while you sleep. Add rate limiting and lockout after 5 failed attempts. This is table stakes.

SHOW FIX

✅ FIXED — express-rate-limit example

middleware/rateLimit.js
import rateLimit from 'express-rate-limit';
export const loginLimiter = rateLimit({
windowMs: 15 * 60 * 1000, // 15 minutes
max: 5, // 5 attempts max
message: 'Too many attempts. Try again in 15 minutes.'
});

"Add rate limiting to my login route and any other auth endpoints. Use a sliding window of 15 minutes with a max of 5 attempts. Return a clear error message. Also add account lockout after 10 total failed attempts across any window."

H-07
HIGH

CORS SET TO WILDCARD (*)

Any website can make authenticated requests to your API using your users' own cookies. Whitelist specific origins only.

SHOW FIX

❌ BAD

server.js
app.use(cors()); // or cors({ origin: '*' })

✅ FIXED

server.js
app.use(cors({
origin: ['https://yourapp.com', 'https://www.yourapp.com'],
credentials: true
}));

"Find my CORS configuration and replace any wildcard origins with an explicit whitelist of allowed domains. Use my production domain and localhost for development. Enable credentials only if needed."

H-08
HIGH

JWTS STORED IN LOCALSTORAGE

One XSS attack steals every token on your site. localStorage is readable by any script on the page. Use httpOnly cookies instead.

SHOW FIX

❌ BAD

localStorage.setItem('token', jwt);

✅ FIXED — httpOnly cookie set from server

res.cookie('token', jwt, {
httpOnly: true, // not readable by JS
secure: true, // HTTPS only
sameSite: 'strict'
});

"Find any JWT or session tokens stored in localStorage or sessionStorage. Move them to httpOnly, secure, sameSite=strict cookies set by the server on login. Update the auth flow accordingly."

H-09
HIGH

WEAK / DEFAULT JWT SECRET

Attackers test common secrets first. "secret", "password", "jwt_secret" are all on wordlists. Generate a 256-bit random secret and rotate it.

SHOW FIX

✅ Generate a strong secret

terminal
# Generate a 256-bit secret and paste into .env
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
# Output goes in .env as JWT_SECRET=abc123...

"Check my JWT configuration. If the secret is hardcoded, weak, or a default value from a tutorial, replace it with a reference to an environment variable. Generate a strong secret using Node's crypto module and show me how to add it to .env."

H-10
HIGH

IDOR — NO OWNERSHIP VALIDATION

Change the ID in the URL. Can you access another user's data? Most vibe coded apps: yes. Validate ownership server-side on every resource request.

SHOW FIX

❌ BAD — fetches any record by ID

app.get('/api/records/:id', async (req, res) => {"{"}
const record = await db.find(req.params.id);
res.json(record); // returns ANY user's record
{"}"});

✅ FIXED — ownership check

const record = await db.find(req.params.id);
if (record.userId !== req.user.id) {"{"}
return res.status(403).json({"{"} error: 'Forbidden' {"}"});
{"}"}

"Audit every GET, PUT, PATCH, DELETE route that takes a resource ID as a parameter. For each one, verify that the route checks whether the authenticated user owns that resource before returning or modifying it. Add ownership checks wherever they're missing."

H-11
HIGH

PASSWORDS HASHED WITH MD5 OR SHA1

Rainbow tables crack MD5 in seconds. No salt = no protection. Use bcrypt or argon2, no exceptions.

SHOW FIX

✅ FIXED — bcrypt

import bcrypt from 'bcrypt';
const hash = await bcrypt.hash(password, 12); // cost factor 12
const match = await bcrypt.compare(attempt, hash);

"Find all password hashing in my codebase. If it uses md5, sha1, sha256, or any non-bcrypt/argon2 method, replace it with bcrypt (cost factor 12). Update the comparison logic to match."

H-12
HIGH

AUTH TOKENS THAT NEVER EXPIRE

Stolen session = permanent access forever. Set an expiry on every token. Implement refresh token rotation.

SHOW FIX

"Check my JWT signing configuration. Add an expiry of 15 minutes for access tokens. Implement a separate refresh token flow with 7-day expiry, stored in the database so it can be revoked. Show the full login, refresh, and logout flow."

🟡 MEDIUM — CLEAN BEFORE YOU PUBLICISE
M-13
MEDIUM

NO HTTPS ENFORCEMENT

Credentials sent over plain HTTP can be intercepted on any public Wi-Fi. Redirect all HTTP to HTTPS at the server level.

SHOW FIX

"Add HTTPS enforcement to my server. Redirect all HTTP requests to HTTPS automatically. Also add the Strict-Transport-Security header (HSTS) with a max-age of at least 1 year."

M-14
MEDIUM

SESSIONS NOT INVALIDATED ON LOGOUT

The old session token still works after the user clicks logout. Client-side cookie clearing is not enough — invalidate server-side too.

SHOW FIX

"Update my logout endpoint to invalidate the session server-side — either by deleting the session record from the database or adding the token to a blocklist. Clearing the client cookie alone is insufficient."

M-15
MEDIUM

ERROR RESPONSES EXPOSING STACK TRACES

You're giving attackers a map of your infrastructure. Log errors server-side, return generic messages to the client.

SHOW FIX

❌ BAD

res.status(500).json({"{"} error: err.stack {"}"});

✅ FIXED

console.error(err); // log full error server-side
res.status(500).json({"{"} error: 'Something went wrong' {"}"});

"Audit all my error handlers. Ensure stack traces, database table names, and internal paths are never returned to the client. Replace them with generic error messages. Full error details should only go to server-side logs."

M-16
MEDIUM

FILE UPLOADS WITH NO MIME TYPE VALIDATION

Upload a server-side script, get full access. Extension checks alone don't protect you — validate MIME type server-side.

SHOW FIX

"Find my file upload handling. Add server-side MIME type validation using the file buffer (not just the extension or Content-Type header). Whitelist only the specific file types my app needs. Reject everything else with a clear error."

M-17
MEDIUM

SERVER RUNNING AS ROOT

One exploit gives full system access. Run your app as a non-privileged user. This costs nothing to fix.

SHOW FIX

✅ Dockerfile / deployment fix

Dockerfile
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser
CMD ["node", "server.js"]

"Check how my application is deployed. If it runs as root (either in Docker or on a VPS), add a non-privileged user and run the app as that user instead. Show me the Dockerfile or systemd service changes needed."

M-18
MEDIUM

DATABASE PORT EXPOSED TO THE INTERNET

Your Postgres on port 5432 should never have a public IP. Put it behind a firewall or private network.

SHOW FIX
HOW TO CHECK

On most cloud providers (Railway, Render, Fly.io, AWS): go to your database settings and confirm there is no public IP or that the firewall blocks port 5432/3306/27017 from all external IPs. Only your app server should be able to reach the database, on an internal network.

"Review my database configuration and deployment setup. Is the database accessible from the public internet? If so, explain how to move it behind a private network or firewall rule that only allows connections from my application server's IP."

M-19
MEDIUM

OPEN REDIRECTS IN CALLBACK URLs

Used to send users to phishing sites through your trusted domain. Validate and whitelist every redirect destination.

SHOW FIX

"Find any routes in my app that accept a redirect URL as a parameter (e.g., ?next=, ?redirect=, ?returnTo=). Add validation so only whitelisted internal paths are allowed. Reject any redirect to an external domain."

M-20
MEDIUM

SECURITY HEADERS MISSING

CSP, HSTS, X-Frame-Options, X-Content-Type-Options. A 2-minute AI prompt gets you a solid baseline. From the Reddit guide — this is the quick win most vibe coders skip.

SHOW FIX

✅ helmet.js (Express)

import helmet from 'helmet';
app.use(helmet()); // sets 15 security headers automatically

"Review my app as a security specialist. Add strong security headers: Content-Security-Policy, Strict-Transport-Security, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, and Permissions-Policy. Use helmet.js if Express, or set headers manually. Explain what each header does."

🟢 LEGAL / COMPLIANCE — PROTECT YOURSELF, NOT JUST YOUR APP
L-21
COMPLIANCE

NO PRIVACY POLICY WHEN COLLECTING USER DATA

If you collect any user data, you need a privacy policy. GDPR, DPDP Act, and most app stores require it. You don't need a lawyer — you need to not be reckless.

SHOW FIX

"Write a basic privacy policy for my app. It collects: [list what you collect — email, usage data, etc.]. Users are primarily from [India/EU/etc.]. Cover: what data is collected, why, how it's stored, who can access it, how users can request deletion, and contact info. Plain English. Keep it honest."

L-22
COMPLIANCE

COLLECTING MORE DATA THAN NEEDED

GDPR data minimisation: only collect what's necessary for your stated purpose. Every extra field is extra liability.

SHOW FIX

"Review my user registration form and database schema. For each field I collect, ask: is this actually required for the app to function? Flag any fields that are 'nice to have' vs 'necessary'. Suggest what to remove to minimise data collection."

L-23
COMPLIANCE

API RESPONSES RETURNING TOO MUCH USER DATA

Your /me endpoint probably returns the full database row including password hash, internal IDs, and fields the frontend never uses. Strip it down.

SHOW FIX

"Check my app as a security specialist and identify any API endpoints returning too much user data. Look for: password hashes, internal database IDs, tokens, or private fields being returned to the frontend. Create explicit response serializers that only return what's needed."

L-24
COMPLIANCE

SECRETS APPEARING IN SERVER LOGS

API keys and tokens logged during debugging end up in your logging service, readable by anyone with log access. Scrub them.

SHOW FIX

"Check my app for any logging statements that might output API keys, tokens, passwords, or other sensitive values. Replace them with redacted versions or remove the logging entirely. Also check if my request logging middleware logs authorization headers."

SURGERY: TDD + PRE-DEPLOY CHECKLIST

You don't need to become a TDD expert. You need 3 prompts that make your AI tools write tests alongside the code — and a 10-point pre-deploy checklist you can run in under 10 minutes.

// 3 TDD PROMPTS FOR CLAUDE CODE / CURSOR

01

TESTS FIRST — BEFORE ANY CODE

Forces the AI to define what correct behaviour looks like before writing the implementation. Catches security assumptions early.

"Before writing any code for this feature, write the tests first. Define: what should this function return for valid input? What should it reject? What are the edge cases? What happens with malicious input? Write the test file first, then implement to make them pass."

02

AUTH MIDDLEWARE WITH FULL COVERAGE

The most common security gap is auth middleware with no tests. This forces coverage of all three cases that matter.

"Add authentication middleware to this route with full test coverage. Write tests for: (1) authenticated user with correct role — should succeed, (2) authenticated user with wrong role — should return 403, (3) unauthenticated request — should return 401, (4) expired or tampered token — should return 401. Implement the middleware to pass all tests."

03

SECURITY REQUIREMENTS FIRST

Use before any new feature. Gets the AI to think adversarially before it writes a single line of production code.

"Before generating any code: (1) List every security requirement this feature must satisfy, (2) Identify potential attack vectors an adversary could use, (3) List the input validation rules needed, (4) State what the function must never do or expose. Review this list with me, then implement with those constraints baked in from the start."

// PRE-DEPLOY CHECKLIST — RUN BEFORE EVERY LAUNCH

  • ☐Run npm audit — zero critical vulnerabilities allowed
  • ☐Grep for hardcoded secrets: grep -r "sk-\|AKIA\|Bearer " . --include="*.js" --include="*.ts"
  • ☐Confirm .env is in .gitignore and never committed: git log --all -- .env
  • ☐Verify every API route has appropriate auth middleware — no exceptions
  • ☐Test rate limiting: send 10 rapid login requests and confirm the 6th is blocked
  • ☐Confirm CORS origins are whitelisted — no wildcard * in production
  • ☐Test error messages: trigger a 500 error and confirm no stack trace is returned to the client
  • ☐Confirm HTTPS redirect is active — http://yourapp.com should redirect to https://
  • ☐Review your API responses: does /api/me return a password hash or unnecessary fields?
  • ☐Run the OWASP audit prompt below against your full codebase

"Review my entire application against the OWASP Top 10. For each vulnerability category, tell me: (1) whether my app is vulnerable, (2) the specific file and line number where the issue exists, (3) the exact fix needed. Prioritise by severity. This is a pre-launch security audit — be thorough."

ICU: POST-DEPLOY MONITORING

Shipping is not the finish line for security. Set up ongoing monitoring habits and know exactly what to do if something goes wrong.

// ONGOING MONITORING HABITS

📦

NPM AUDIT ON EVERY DEPLOY

Add npm audit --audit-level=critical to your CI/deploy script. It should block the deploy if criticals are found. The TanStack attack would have shown up here.

🔔

API KEY USAGE ALERTS

Set spending limits and usage alerts on every API key (OpenAI, Anthropic, Google). A bill-shock alert at $10 over baseline catches a leaked key before it becomes a $10,000 problem.

🔍

GITHUB SECRET SCANNING

Enable GitHub's free secret scanning on your repo. It automatically detects API keys from 200+ providers committed to your history and notifies you immediately.

📋

ERROR LOG MONITORING

Watch your server error logs for unusual patterns — repeated 401s on /admin, massive spikes in traffic, errors from unexpected geographies. These are often your first signal of an attack.

⬤ CODE BLUE ALREADY SHIPPED WITH A VULNERABILITY? HERE'S YOUR TRIAGE PROTOCOL.

Don't panic. Work through this list in order. Speed matters more than perfection right now.

  1. ROTATE THE LEAKED KEY — IMMEDIATELY Go to your API provider dashboard right now. Revoke the exposed key and generate a new one. Do this before anything else. Deleting the file is not enough — the key is already compromised.
  2. FIND ALL COMMITS CONTAINING SECRETS git log --all --full-history -- .env
    git log --all -S "YOUR_KEY_VALUE" --source --all
  3. PURGE THE HISTORY Use git filter-repo (recommended) or BFG Repo Cleaner to remove the secret from all commits. Force-push the cleaned history. Warn collaborators first.
  4. AUDIT API USAGE LOGS Check your API provider's usage logs for the period the key was exposed. Look for requests you didn't make — unusual volumes, unknown endpoints, or requests from unexpected regions.
  5. ASSESS DATA EXPOSURE If user data was accessible: what was exposed? Who could have accessed it? For how long? Document this carefully — you may need it for the next step.
  6. NOTIFY AFFECTED USERS IF REQUIRED GDPR requires notification within 72 hours if personal data was likely exposed. DPDP Act (India) has similar requirements. Even if not legally required, notifying users is the right thing to do. Be specific about what happened, what was exposed, and what you've done.
  7. PATCH AND RE-DEPLOY WITH FIXES APPLIED Don't re-deploy until the original vulnerability is fixed. Use the checklist in Section 04 before the new deploy goes live.
